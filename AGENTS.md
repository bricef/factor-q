## Guidance

Every code change MUST include a documentation pass before the task is considered complete. After making any code change, identify which docs could be affected (AGENTS.md, README.md, ARCHITECTURE.md, and the relevant docs/ topic files) and update them in the same change so the docs do not drift from reality. If the change is genuinely doc-irrelevant (a typo fix, a pure dependency bump, a no-op refactor), say so explicitly rather than silently skipping the pass. Treat updated docs as part of the deliverable — do not defer them to "later".

Consider writing an ADR whenever you are planning a multi-step or large-blast-radius architectural change — anything spanning multiple PRs or phases, anything that establishes a pattern or forecloses an alternative, anything touching the simulation engine, persistence shape, concurrency, payments, or deploy. Bug fixes, dependency bumps, local refactors, and features that fit cleanly inside an existing pattern do not need an ADR. When unsure, propose one in the planning phase rather than after the fact.

ADRs are immutable once accepted. Treat them like database migrations: never rewrite the body of an accepted ADR to reflect a later decision. When a decision evolves, capture it in a new ADR rather than editing the old one — both supersession and refinement keep the spirit of immutability. If the new ADR reverses or replaces the prior decision, it **supersedes** it (`Supersedes ADR-NNNN` in its Status line, and the prior ADR's Status line gains a `Superseded by ADR-MMMM` pointer). If the prior decision still stands but the new ADR extends or adjusts its rationale — or records newly-discovered detail — it **refines** it (`Addendum to` / `Refines ADR-NNNN` in its Status line, and the prior ADR's Status line may gain a brief `Refined by ADR-MMMM` pointer). In both cases the only change to the prior ADR is a short forward-pointer on its Status line; the decision and reasoning in its body are never rewritten. Typo fixes, dead-link repairs, and markdownlint corrections are not revisions and are fine.

Keep docs/adrs/README.md in sync. Every new ADR file must be added to the index in the same change. Every markdown file under docs/ (every ADR and the index included) must pass markdownlint with zero errors — run `just lint-docs` (`just lint-docs --fix` auto-corrects the mechanical rules). Cite PRs and issues with full URLs, not bare numbers.

Built-in tools follow a construction convention. Every tool struct pairs `#[derive(Default)]` with an explicit `pub fn new() -> Self` and is registered as `Arc::new(XTool::new())` in `ToolRegistry::with_builtins` — even a stateless unit-struct tool. The `new()` is a forward-compatible seam, not boilerplate: it lets a tool gain configuration later without churning any construction site (see `ExecTool`, which grew an `ExecConfig` and a `with_config()` while every caller kept using `new()`). Match this when adding a tool rather than registering the bare struct literal.

Rust code is organised as real module trees — `include!` is banned repo-wide, enforced by `just lint-sources` (a git-grep source gate, run as a phase of `just quality`). `include!` splices source files into one translation unit behind the tooling's back: rustfmt only discovers files through `mod` declarations, so a spliced file is silently never formatted again, and clippy's `disallowed-macros` cannot see `include!` invocations at all, which is why the gate is a source scan rather than a clippy config. The same gate rejects `include_str!`/`include_bytes!` aimed at `.rs` files — embedding source as data is the same splice one step removed; scanners such as the fq-cli `store_open_gate` test read the tree at runtime instead. Embedding non-source data (templates, web assets) with `include_str!` remains fine. There is no allow-marker: splitting a large file means real modules with `mod` declarations and per-module `use` blocks, and the `include!` ban is absolute. If a future `include_str!` use is genuinely valid and trips the gate, allow it case by case — narrow the gate's pattern or exempt that specific path in the `lint-sources` recipe, as its own reviewed change — rather than contorting otherwise-clean code around the lint; a deliberate gate exemption beats convoluted evasion every time. Origin: <https://github.com/bricef/factor-q/pull/322>.

Restructure, don't append. Two size budgets are enforced by `just lint-sizes`, run as a phase of `just quality`: no file may exceed **800 production lines** and no function may exceed **250 lines**. Offenders that predate the gates are pinned in `.file-size-baseline` and `.function-size-baseline` and may only ever shrink. "Production lines" means total minus `#[cfg(test)]` items, so adding tests is always free — the budget bounds production complexity, not test coverage; test functions are likewise out of scope. Functions are measured from the `fn` keyword, never from the start of the item, so a function is never charged for its own doc comment. Unit tests belong in a sibling file — `#[cfg(test)] mod tests;` beside `foo.rs` in `foo/tests.rs` — so a file's production code is not buried under its own tests; `fq-lint` resolves the declaration and excludes the backing file from both budgets, transitively. The measurement runs off a real `syn` AST (`tools/fq-lint`), never a text scan, so it either parses the file exactly or fails loudly; a hand-rolled scanner was wrong on three of the tree's 140 files. Note the boundary with clippy is *threshold versus ratchet*, not files versus functions: clippy can say "no function over N" (`too_many_lines`) but cannot say "*these* functions must shrink", because its thresholds are global with no per-item baseline and the only escape is an `#[allow]` at the site — a permanent pass rather than a shrinking budget. Anything clippy can already express, leave to clippy; do not reimplement its lints in `fq-lint`. `just lint-creep` is the early warning for the function gate. It lists production functions that are either over 150 **code** lines (comments and blanks excluded) or within 50 physical lines of the cap — two prongs, because the gate measures physical span, so a comment-heavy function can sit under the code threshold while being a line or two from blocking a merge. Output is ordered by headroom, so the function that will trip next is the first one you read. It is **advisory and always exits 0**. It is computed from the AST rather than by shelling out to `clippy::too_many_lines`, which measures the same idea but cannot be trusted here — `cargo clippy -- --force-warn <lint>` does not invalidate cargo's fingerprint, so cached units never re-emit, and on this tree it reported 13 functions where a full rebuild found 35. The gate exists because LLM agents overwhelmingly append to existing structures rather than restructure them, and at fleet speed that turns large files into god-files faster than reviews can pay them down: three split issues stayed open across two cleanroom reviews while every file they named grew (`runner.rs` 5.6k→7.4k, `fq-cli/src/lib.rs` 4.4k→6.3k). **If your change trips either gate, stop.** Do not raise a budget in `.file-size-baseline` or `.function-size-baseline`, and do not opportunistically restructure the file as a side effect of an unrelated change — those files are being split under their own issues (<https://github.com/bricef/factor-q/issues/78>, <https://github.com/bricef/factor-q/issues/189>, <https://github.com/bricef/factor-q/issues/191>) and a drive-by split collides with that work. Put new code in a new module, or say on the PR that the change genuinely belongs in that file and let a human decide at the merge gate. Budgets may only ever go down: `just sizes-bless` lowers them to match reality and refuses to raise any or admit a new entry, so shrinking a file or function permanently tightens its budget. Origin: `docs/reviews/2026-07-25-factor-q-cleanroom-review.md` Part 2.

Coupling is reported, not yet gated. `just lint-coupling` (a phase of `just quality`, **advisory and always exits 0**) reports each crate's top-level module graph: production lines, fan-out, fan-in, and import cycles. It exists as the counterweight to the size ratchets — a file-size budget on its own rewards the wrong refactor, because splitting a god-file into two halves that import each other heavily passes `just lint-sizes` and leaves the tree worse, and nothing else in `just quality` can tell that split apart from a real one. Cycles matter because Rust forbids *crate* cycles but permits *module* cycles silently, so no other tool in this repo sees them; they are reported as strongly connected components, not mutual pairs, because a three-module cycle contains no mutual pair and a pairwise check would call it clean. Edges are `crate::`- and `super::`-rooted paths in production code, read off the same `syn` AST as the size gates and counted between **top-level** modules only (`worker`, not `worker::reducer::runner`). Two consequences worth knowing: a re-export or a trait-method call reaches a module without naming a path, so every count is a **floor** and never an over-estimate; and a doc-comment link like [`crate::agent::AgentId`] is not a dependency, so cross-referencing in documentation is free. On a PR, `scripts/coupling-pr-comment.sh` (the `Coupling metrics` CI job) diffs the branch against its merge base and keeps one self-renewing comment showing what changed — the same binary measures both sides, so editing `fq-lint` itself can never masquerade as a tree-wide coupling shift. **Nothing here blocks a merge**; treat a new cycle or a jump in fan-out as a question to answer on the PR, not an error. Origin: `docs/reviews/2026-07-27-code-quality-metrics.md`.

Goldens catch the change you did not mean to make, and a broken golden is answered in a fixed order. **First**, treat it as a regression: has behaviour that should have held stopped holding? **Second**, if the change was deliberate, check the diff is *exactly* what you intended and nothing more — a golden's value is showing you the blast radius of a change you thought you understood. **Only then, as a last resort**, consider whether the golden's expectation was itself wrong. The order matters: reaching for the third question first turns every inconvenient failure into "the golden was wrong", which is how a suite stops being worth running. That third case is real but rare — `workers_list_*` expected a roster with no daemon row though `run_daemon` has always self-registered one, and recorded a worker `alive` with a stale heartbeat that the coordination sweep repairs on sight (<https://github.com/bricef/factor-q/pull/448>). When it does happen, fix the *fixture* rather than the expectation file, and record at the fixture why the old expectation could not occur, so a later reader does not mistake it for a golden weakened to make a change pass. **Any PR that modifies a golden says why in its description.** Deliberate behaviour changes are allowed to move goldens — the gate is review, not the file — but a golden diff is looked for at review, and an unexplained one is a defect in the PR.

A ratchet measures what it matches, not what exists. `edge_migration_gate.rs` counts the operator surface's remaining legacy call points and is meant to reach zero, and it has twice gone *up*: 6→7 when the counted patterns grew to include the CLI's own disk read of the agent registry, and 7→9 when they grew to include client-side bus subscribes. Neither was a regression. Each widening admitted call points that had been there all along and simply sat outside the pattern — verb 5's in-process `fq trigger` in the first case, `fq down`'s two subscriptions in the second. **Discovery that raises a count is the gate working as intended, not a problem.** What matters is capturing the true state, not making a number fall: a narrow pattern buys a tidy downward line while real backlog stays invisible, which is worse than an honest larger number. Aim for full coverage, and before trusting a change to move a ratchet, confirm the ratchet actually counts the path being removed — if it does not, widen it first and expect the number to rise. Origin: <https://github.com/bricef/factor-q/pull/448>, <https://github.com/bricef/factor-q/pull/455>.

A command that exits 0 having done nothing is not a passing check, and the two easiest ways to produce one are operator error rather than a weak gate. Shell pipelines report the *last* command's status, so `cargo test | tail` prints 0 over a failing suite — when an exit code is the thing being judged, redirect to a file and read `$?`, or set `pipefail`. And a skip list is an exit-0 machine when it matches too much: `.claude` is agent scratch, excluded from the documentation checks (`SKIP_PARTS` in `scripts/check-links.py`), and that exclusion was matched against each file's *absolute* path, so a worktree at `.claude/worktrees/<name>` — the repo's own standard layout — took its entire tree out of the checker's view and reported "0 relative links checked", exiting 0 without reading a single file. `SKIP_PARTS` is now matched against each file's path *relative to the root being scanned*, so the root's own address can never disable the check while nested scratch, build output and nested worktrees stay skipped; a scan that reads zero markdown files is a failure rather than a pass; and the summary line reports the file count beside the link count, so "did it do work?" is answerable from the output. Worktrees under `.claude/worktrees/` are checked normally — no copy outside that path is needed. The same shape catches test filters — `cargo test --exact` with a truncated name matches nothing and exits 0. When a check passes, confirm it reported doing work.

Build artifacts are the largest thing this repo produces, and a `target/` directory is per *worktree*, not per repo. A full build runs to roughly 20G, so a handful of agent worktrees outgrow everything else on the machine — and the failure mode is nasty, because ENOSPC does not announce itself: it truncates files in working trees and reaches whoever is building as a compile error rather than as a full disk. Three habits keep it bounded. **Remove a worktree once its branch merges** — the work is on `main` and the target directory is dead weight nothing reclaims (`git worktree remove`, then `git worktree prune`); create worktrees with `wt` so they land outside `.claude`. **Do not run cargo for a documentation-only change** — `just lint-docs` is the gate for docs and compiles nothing, so reaching for `just quality` or a test suite to verify a markdown edit builds the entire workspace for no signal. **Check free space before starting parallel work**, because two concurrent full builds want 40G between them. `[profile.dev] debug = "line-tables-only"` in the root manifest is the standing half of this: backtraces keep file and line, which is what a panic or a failing test needs, and the variable-inspection data a debugger would want is the price — override it per-session with `RUSTFLAGS="-C debuginfo=2"` rather than changing the manifest.

CI runs through `just`. Every GitHub Actions job invokes a `just` target rather than raw cargo/npx/tooling, so the CI environment stays isomorphic with local dev — what passes under `just ci` locally passes in CI. Toolchain setup steps (Rust, Node, just itself) are the only non-`just` glue, since they must exist before `just` can run. Split CI into separate jobs by concern — e.g. docs lint (`just lint-docs`); every non-test quality gate in one Code quality job (`just quality`: the `include!` scan, the file and function size ratchets, workspace fmt, clippy over every crate, and the advisory function-length creep report), so one command answers whether the tree is clean and clippy compiles the workspace once instead of per suite; and the Rust gate split into a runtime job (`just runtime-ci`, whose NATS-backed tests spawn their own broker from the pinned `nats-server`, plus Node for the MCP tests) plus a store job whose grant-bus test spawns its own broker likewise (`just store-ci`) and a hermetic dashboard job (`just dashboard-ci`) so one suite's failure never masks the others — each calling its own target. `just ci` invokes those same targets rather than re-implementing them, which is what keeps the local gate and CI from drifting: adding a suite to CI means adding its target to `just ci`, and nothing else.


Repo-specific agent skills live in `meta/skills/<name>/SKILL.md` — repeatable procedures with their utility scripts colocated (e.g. regenerating `docs/design/committed/architecture-diagram.*` from source). When a task matches one, read its SKILL.md and follow it. `.claude/skills/` contains only thin tracked shims that defer to `meta/skills/`, so the procedures themselves stay agent-agnostic; add new skills as a `meta/skills/` directory plus a shim, matching `meta/README.md`.
